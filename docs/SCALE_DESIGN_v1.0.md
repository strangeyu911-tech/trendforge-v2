# TrendForge V2 规模化设计 `SCALE_DESIGN_v1.0`

> 关于"规模化"，本文交付的是**思考框架**而非玩具级实现：若日活千万、日产 10 万条，架构如何演进；以及哪些"听起来该做"的事我们**评估过但有意不做**，理由写清。
> 设计基线：当前是单进程 FastAPI + SQLite + BM25 + 同步 LLM 调用的 Demo 架构（见 README）。以下演进不推翻"拓扑固定、行为可配"的原则，只把**执行层**从单进程搬到分布式。

---

## 1. 当前架构（基线，便于对照）

```
                 ┌──────────── FastAPI 单进程 ────────────┐
 请求 POST /run ─┤ asyncio.create_task(run_pipeline)       │
                 │   Sense→Produce→Amplify（10 步固定拓扑） │
                 │   LLM 同步调用（DeepSeek）              │
                 │   结果写 SQLite + 市场级缓存             │
                 └────────────────────────────────────────┘
                       BM25(KB) · signals 72h 缓存 · 逐级规则降级
```

**它能跑多少**：单市场一次供给约 60–180s（取决于 LLM 延迟）。单进程串行下，一天约能产数百条。对 Demo / 作品集足够，但对"日产 10 万"差 2–3 个数量级。

---

## 2. 演进路线（日产 10 万条 / 千万 DAU）

### 2.1 异步化与任务队列（第一步，必做）
把 `run_pipeline` 从"请求内 `asyncio.create_task`"升级为**消息队列 + Worker 池**。API 只接任务、返回 `task_id`；Worker 拉取执行。
- 解耦：HTTP 延迟与供给延迟解绑，API 永远快返回。
- 背压：队列长度即"待产积压"，可熔断与限速。
- 选型：Celery / RQ / 云原生队列（SQS/Redis Streams）。Worker 无状态，可随意扩缩。

### 2.2 按市场水平分片（第二步）
5 个市场（US/JP/KR/BR/CN）各自一组 Worker + 独立 LLM 配额 + 独立 KB 索引。
- 信号源按市场分片拉取，避免 5 个市场抢同一外部 API 配额（尤其 HN/Dev.to 限流）。
- 跨市场无共享状态，分片失败不影响其他市场——天然隔离故障域。

### 2.3 缓存与选题去重（第三步，省成本大头）
- 信号缓存（已做 72h TTL）→ 升级为"信号指纹 + 选题指纹"：同一选题 24h 内命中直接复用母稿派生，不重跑 LLM。
- 内容级去重：用 `topic+angle+market` 哈希做幂等键，防止重复供给吃掉预算。

### 2.4 LLM 成本路由（第四步）
不是所有 Agent 都该用最贵模型：
- **贵模型**（推理强）：`Writer` / `Editor`（创作与裁决，质量敏感）。
- **便宜模型**：`SignalScout` 摘要、`AudienceInsight` 归类、`FormatAdapter` 模板截取。
- 设**每日成本 cap + 熔断**：预算触顶自动降级到便宜模型 / 规则兜底，不让单日成本失控。

### 2.5 审核抽样率（第五步，规模化的关键取舍）
当前**全量 Editor 审核**（每条都过 Rubric）。日产 10 万时改为**风险分层抽样**：
- 高危类目（政治 / 健康 / 金融 / 合规敏感）→ **全量**审核。
- 低风险类目 → **5–10% 抽样** + 硬规则合规扫描（现有 `COMPLIANCE_BLOCKLIST`）兜底 + 人工抽检。
- 抽样结果回流 `BadCase`，动态调整抽样率（某类目 bad_case 升 → 抽样率自动上调）。
- 这一机制本身就是 `FeedbackAnalyst` 闭环的规模化版。

### 2.6 存储与可观测性（配套）
- SQLite → 读写分离（PostgreSQL 主 + 列存分析只读副本）；内容冷数据归档对象存储。
- Trace/span 已结构化（`task_spans` 含 token/耗时/状态）→ 接 OpenTelemetry/Prometheus，成本与质量看板实时化（M2 分析中心的规模化延伸）。

### 演进架构图

```
            ┌─────────── API 网关（只接任务/查状态）───────────┐
            │                                               │
       [任务队列] ──┬── Market Shard US (Worker×N + LLM配额) │
                    ├── Market Shard JP (Worker×N + LLM配额) │
                    ├── Market Shard KR / BR / CN ...        │
                    └── Dead-letter（失败重试/人工兜底）      │
            │            │                      │            │
        PostgreSQL   BM25/向量分片       Prometheus/OTel
        (读写分离)    (KB 按市场分片)     (成本/质量实时看板)
```

## 3. 成本模型（日产 10 万条的账）

基于真实单价（`config.py`：`deepseek-v4-flash` 入 ¥2/1M、出 ¥8/1M）与实测单条 token（3–8 万，取中枢 5 万：入 4 万 / 出 1 万）。

| 项目 | 计算 | 日成本 | 月成本 |
|---|---|---|---|
| 单条 LLM 成本（中枢） | 40k×¥2/1M + 10k×¥8/1M | ≈ ¥0.16 | — |
| 日产 10 万条（全量贵模型） | 0.16 × 100,000 | ≈ ¥16,000 | ≈ ¥48 万 |
| 成本路由后（约省 40%） | ×0.6 | ≈ ¥9,600 | ≈ ¥29 万 |
| 选题去重命中 30% | ×0.7 | ≈ ¥6,700 | ≈ ¥20 万 |

**对比人工**：10 万条/日深度内容，若由人类编辑产出（单条保守 45min），需 ≈ 7,500 人日/日，物理上不可行。供给引擎的价值不在"比人写得好"，而在"**把边际成本从'人力线性'压到'算力近常数'**"——这是内容供给生意的底层经济学。

> 边界声明：以上为**工程估算**，非已实测的 10 万条账单。真实规模还需压测 LLM 吞吐与限流。成本是"可推演的区间"，不是精确承诺。

## 4. 已评估但未做（"不做"也是设计）

每一项都**评估过、有意识放弃**。这比"什么都做一点"更值钱。

| 项 | 为什么评估要做 | 为什么现在不做 | 何时会做 |
|---|---|---|---|
| **审核分层**（事实/合规/质量/文化四层独立） | JD 提到多层审核 | Demo 规模下分层增加延迟与失败面；现状"Editor 单点裁决 + 硬规则合规扫描"已覆盖其要解决的问题，且可说明"评估过拆分，延迟成本不划算" | 日产 10 万进入抽样审核时自然分化 |
| **DAG 编排**（可拖拽工作流） | 显得灵活 | 固定拓扑是领域最佳实践，DAG 带来调度复杂度与可观测性黑洞；"拓扑固定、行为可配"是有意判断 | 若出现大量异构任务类型才考虑 |
| **向量检索**（替代 BM25） | 跨语言语义检索更强 | Demo 规模 BM25 足够、零依赖、接口可插拔；跨语言语义检索才真需向量 | 信号真实化、多语言 KB 膨胀后 |
| **多模态渲染**（视频/音频/海报成片） | 形态更完整 | 无多模态 API（用户已确认）；渲染层是明确边界 | 接入渲染 API 即接，接口已就位 |
| **社媒趋势信号**（X/Reddit/Naver 趋势等感知源） | 需求侧信号、本地话题 | Reddit datacenter IP 403（实测）、X 读取档付费、无官方 API 的趋势榜有合规风险；本地语言新闻已由 GDELT sourcecountry+sourcelang 覆盖 | 分级路线见 [SOCIAL_SIGNAL_DESIGN_v1.0.md](SOCIAL_SIGNAL_DESIGN_v1.0.md)：免费官方 API 先行 |
| **AI 自动调优**（自动改 Prompt/参数） | 闭环更"智能" | 会摧毁"人定义标准"核心叙事 | 永不——坚持"提议—人审—采纳—可回滚" |

> 第 5 项是最关键的产品判断：全自动调优看似高级，但"人定义标准"是本项目对"AI Native PM"岗位的核心回答。我们复用 KBCurator 的"AI 提议 + 人审闸门"模式做闭环，保住叙事也保住可控性。

## 5. 规模化的"不变项"

无论规模怎么扩，以下原则不动（它们是项目身份，不是技术债）：
1. **拓扑固定、行为可配**：链路顺序不变，可配的是 Prompt / 市场档案 / Rubric。
2. **人定义标准**：市场档案、Prompt 模板、评估 Rubric 始终是人维护的一等公民。
3. **事实可溯源**：LLM 不联网，KB 是唯一事实来源，`[ev]` 引用链不变。
4. **逐级降级、主链路不裸奔**：任何环节失败走规则兜底，规模下这更是稳定性基石。

## 6. 与里程碑的关系

- 当前 Demo 已为每个演进点埋了"接缝"：`TaskSpan` 结构化→可观测性；`settings.formats`/`max_review_rounds` 可配→成本路由与抽样率；`PipelineCache`→选题去重；`BadCase`→抽样率动态调节。
- M2 分析中心是"可观测性"的雏形；M3 闭环是"抽样率动态调节"的雏形。
- 本文档是"规模思考"交付物，按 `ITERATION_PLAN` 约定以一页文档 + 架构图解决，性价比远高于真写一套分布式系统。
