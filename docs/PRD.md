# TrendForge V2 — PRD
> AI Native 全球化内容供给引擎 · 个人作品集项目

## 0. 一句话定位

TrendForge V2 是一个**把内容供给的关键流程交给 AI 的系统**：AI 负责信号捕捉、趋势研判、需求洞察、角度设计、素材寻找、生成、核查、审核、形态派生、分发策略；人负责定义标准（Prompt / 市场档案 / 评估 Rubric）、判断方向、消费反馈驱动迭代。

> V1 证明"AI 能走完内容生产链路"；V2 回答的是 JD 的真问题——**"AI 能不能像一支内容团队一样，理解市场、做出判断、产出多形态内容、并在反馈中进化？"**

## 1. 背景与问题

传统信息流内容供给的三个结构性瓶颈：

| 瓶颈 | 表现 | V2 的解 |
|------|------|---------|
| 供给靠人追 | 编辑人工刷热点、凭感觉选题，规模化和全球化都做不动 | SignalScout + TrendAnalyst：信号流→趋势研判自动化 |
| 判断不可沉淀 | "什么值得做、什么角度好"存在于老编辑脑子里 | AudienceInsight + AngleEditor：判断显性化为 Brief + 决策日志 |
| 生产=写文章 | 图文一种形态打所有平台所有市场 | FormatAdapter：一次生产、多形态派生（图文/短视频/摘要卡/快讯/评论引导） |

## 2. 目标用户与场景

**用户**：内容供给运营 / 内容策略 PM（Demo 中由访客扮演）。

**核心场景**：
1. 运营选定目标市场（如"日本"）→ 一键跑供给流水线 → 得到一篇带完整证据链、多形态派生、分发计划的内容。
2. 运营查看每条内容的 **Trace**（13 个 Agent 各自做了什么、为什么）→ 判断系统决策是否可信。
3. 运营在**评估中心**看消费数据（CTR/完播/互动/负反馈）与质量 Rubric → 看到系统给出的迭代建议 → 调整 Prompt 或市场档案，闭环。

## 3. 产品架构：供给引擎四段式

```
┌──────────── SENSE 感知 ────────────┐
│ 1 SignalScout      信号捕捉         │  实时拉取 HN / Dev.to / GDELT，归一化为信号流
│ 2 TrendAnalyst     趋势研判         │  聚类→趋势，评估热度/生命周期/跨市场潜力
│ 3 AudienceInsight  需求洞察         │  结合市场档案回答"用户为什么关心"
│ 4 AngleEditor      角度设计         │  输出 ContentBrief（选题+角度+钩子+形态建议）
├──────────── PRODUCE 生产 ──────────┤
│ 5 Researcher       素材寻找         │  query 改写 + RAG 检索证据（强制可溯源）
│ 6 Writer           生成             │  按 Brief + 证据成稿，强制 [ev_xxx] 引用
│ 7 TopicGuard       主题一致性闸门    │  TCS 评分拦截漂移节，定点重写/删节兜底
│ 8 FactChecker      事实核查         │  论断↔证据核对，独立于质量审核
│ 9 Editor           总编审核         │  质量 Rubric + 合规 + 文化敏感性，pass/revise/reject
├──────────── AMPLIFY 放大 ──────────┤
│ 10 FormatAdapter   形态派生         │  一稿多发：短视频脚本/摘要卡/快讯/评论引导
│ 11 Distributor     分发策略         │  平台×受众×时段 分发计划（tool-calling 查本地时间/高峰）
├──────────── EVALUATE 进化 ─────────┤
│ 12 FeedbackAnalyst 反馈分析         │  消费数据→评估报告→迭代建议（回流 Prompt/档案）
│ 13 KBCurator       知识库策展        │  覆盖度/过期扫描→待审补丁（人审闸门）
└────────────────────────────────────┘
```

**三段式 + 一条进化回路**，对应 JD 的四项职责：
- SENSE ≈ "主导当地内容生态与用户需求洞察"
- PRODUCE ≈ "建设 AI Native 内容供给系统"
- AMPLIFY ≈ "设计内容形态与分发策略"
- EVALUATE ≈ "建立数据反馈与智能迭代闭环"

## 4. 核心设计原则（关键取舍）

1. **拓扑固定，行为可配**（沿用 V1 验证过的原则）。供给链路顺序是领域最佳实践，不做可拖拽 DAG；可配的是 Prompt 模板、市场档案、Rubric、参数。
2. **判断显性化**。每个 Agent 产出 `_decision`（为什么这么做），全链路决策日志可在 Trace 页复盘。AI 不只是执行，还要"说清楚为什么"。
3. **人定义标准，AI 执行与进化**。人的入口是三个"标准文件"：Prompt 模板、市场档案（MarketProfile）、评估 Rubric——这就是 JD 说的"人负责定义标准、设计系统"。
4. **形态派生 ≠ 主链路节点**。多形态是"派生器"，主链路只产出经过核查审核的"母稿"，派生器消费母稿，保证任何形态的内容事实可溯源。
5. **Demo 级可靠性**：异步 Job + 结果缓存 + 模型重试/降级，任何路径不裸 500。

## 5. 功能范围（MVP）

| 模块 | 功能 | 优先级 |
|------|------|--------|
| 供给流水线 | 10 Agent 主链路 + 异步 Job + 缓存 | P0 |
| 市场档案 | 5 个市场（US/JP/KR/BR/CN）档案：语言/文化语境/兴趣/禁忌/平台 | P0 |
| RAG 知识库 | 预置 KB（中英新闻精选）+ BM25 检索 + 引用溯源 | P0 |
| 多形态派生 | 短视频脚本 / 摘要卡片 / 快讯 / 评论引导 | P0 |
| Trace 可解释 | 每步 span（token/耗时/状态）+ 决策日志 | P0 |
| 评估中心 | 消费事件模拟 + 漏斗/CTR/完播 + 质量 Rubric + 迭代建议 | P1 |
| Prompt 管理 | 模板文件 + 版本记录（内容存所用版本） | P1 |
| A/B 实验 | 不做（V1 经验：过度设计，ROI 低） | ✗ |

## 6. 关键页面（UI 流程）

```
门户页(/)                → 项目故事 + 入口
控制台(/console/)
  ├─ #overview  仪表盘    → 供给量/市场分布/最新内容/系统状态
  ├─ #markets   市场档案  → 7 市场卡片（文化语境/兴趣/禁忌/平台/洞察依据）
  ├─ #pipeline  跑供给    → 选市场+模式 → 异步 Job 轮询 → 结果卡片
  ├─ #contents  内容列表  → 市场/状态筛选
  ├─ #content   内容详情  → 母稿(引用标注) | 多形态Tab | 分发计划 | Trace | 评估
  └─ #eval      评估中心  → 漏斗/CTR/完播/Rubric 分布/迭代建议
```

## 7. 成功指标（Demo 叙事用）

- 端到端跑通：单市场一次完整供给 ≤ 5 分钟（异步），缓存命中秒开。
- 可解释：任意内容可展示 10 步 Trace + 每步决策理由。
- 可溯源：母稿 100% 事实句带 [ev_xxx] 引用，FactChecker 覆盖率 ≥ 90%。
- 多形态：每条内容 ≥ 3 种派生形态。
- 闭环：评估中心能给出至少一条结构化迭代建议。

## 8. 非目标（明确不做）

- 可拖拽 DAG 编排器（见设计原则 1）
- 真实用户/账号体系、真实分发对接
- 商业化级监控告警、多租户、向量数据库集群
- UI 精修（MVP 后交低成本模型迭代）
