# TrendForge V2 迭代计划 v1.0

> 目标：把项目从「架构完整的概念验证」推进到「摸得到真实业务的系统」。
> 判断标准不是「JD 里提到的关键词有没有覆盖」，而是 **「这个洞被面试官追问时，我会不会答不上来」**。

---

## 0. 对现有差距分析的取舍

外部分析（豆包）按 JD 逐条对照打分，结论方向对，但存在两个方法论偏差：

1. **清单式思维**：把「JD 提到但项目没有」等同于扣分。真实面试不会逐条核对 JD，面试官会挑项目里**最像真的那一处**深挖。所以「缺口宽度」不重要，**「被追问时的答案质量」**才重要。
2. **把「不做」默认当成缺陷**：一个有取舍的 PM，「明确不做且说得出为什么」比「什么都做了一点」更值钱。

因此本计划把候选项分成三档：**要补的洞**、**要换个做法补的洞**、**明确不做但要写进文档的**。

### 采纳
| 外部建议 | 采纳理由 |
|---|---|
| 信号源不真实 | **最致命**。整个引擎的入口是假的，一句「你的热点信号从哪来」就能击穿链路真实性。且修复成本极低。 |
| SQL 能力没体现 | 同意。JD 明确写了 SQL，而这是**能力型**要求，不是功能型——必须有可展示的证据。 |
| 指标维度不全 | 同意方向，但**指标口径要改**（见下）。 |
| PM 视角不足 | 同意，且这对**校招 PM 岗**是最要命的一条。现有 docs 全是技术设计文档。 |

### 采纳但换做法
| 外部建议 | 原方案问题 | 改为 |
|---|---|---|
| 「数据全是模拟的，要接真实数据」 | 真实**分发消费数据**（点击/完读）任何校招生都拿不到——没有产品、没有用户。硬造只会更假。 | 抓取信号时**顺带保留真实互动数据**（HN score/comments、Reddit ups、GDELT tone/volume）作为**真实消费锚点**；后置分发数据保留参数化仿真，但用真实锚点校准，且 UI 明确标注「仿真」。→ 从「数据是假的」变成「前置信号真实、后置分发诚实标注为仿真」。 |
| 「补留存指标」 | 留存是**用户主体**指标，项目里没有用户实体，硬做必假。 | 换成**内容侧 + 供给侧**指标：内容衰减曲线、信号→发布 lead time、一次通过率、降级率、单条成本。这才是「内容供给引擎」该有的指标。 |
| 「闭环缺执行层，要自动调优」 | 全自动调优会直接摧毁「人定义标准」的核心叙事。 | 复用项目内**已有**的 KBCurator 模式（AI 提议 + 人审闸门）：建议结构化 → 人一键采纳 → 生成 Prompt 新版本 → 可回滚 → 下轮对比。既补执行层，又保住叙事，而且**是自己项目内部模式的延伸**，讲起来自洽。 |
| 「加改写 Agent 做多版本」 | 单独立项性价比低。 | 并入 A/B 模块：同一选题跑两版 Prompt → 两个版本内容 → 对比。一石二鸟。 |
| 「规模化感不足，加队列/并发/调度」 | 真写分布式调度成本高、风险大，做出来也是玩具级。面试官问规模问题要的是**思考**不是实现。 | 写一份《规模化设计说明》+ 架构演进图。一页文档解决，性价比高一个数量级。 |

### 不采纳
| 外部建议 | 不做的理由 |
|---|---|
| 审核拆成事实/合规/质量/文化四层 | 为分层而分层，链路更慢、失败面更大，且不会被问到。现状可以正面回答：「评估过拆分，Demo 规模下延迟成本不划算」——这本身就是取舍叙事。写进「已评估未做」清单。 |
| 单独补新闻评论 / 热点事件垂类 | 接入真实新闻源后垂类自然变宽，无需单独立项。 |
| 视觉 / 视频 / 音频 / 混剪 | 无多模态 API（用户已确认）。写进「边界说明」，正面回答：形态派生的产品设计与技术接口已就位，缺的是渲染层。 |

### 外部分析未提、但我认为价值最高的两项
1. **成本 / ROI 看板**——内容供给引擎的核心商业问题是「单条内容的边际成本」。项目的 span 里**已经存了 token 和耗时**，只是没聚合成「单条 = X token = Y 元 vs 人工 Z 分钟」。这是**成本最低、PM 味最浓**的一条。
2. **《真实运行报告》**——与其回避「这系统在真实场景验证过吗」，不如正面交卷：用真实新闻源跑 30 条，交出成功率、失败归因、耗时、成本、Rubric 分布。**不需要真实用户，需要的是真实输入 + 可量化产出。**

## 1. 迭代路线

四个里程碑，每个对应一个 Git tag。**M1 / M4 可并行，M2 依赖 M1，M3 依赖 M2。**

> **当前进度（截至 2026-08-07）**
> - ✅ **M1 真实信号接入** `v2.2-real-signals` — 已完成（HN Algolia / Dev.to / GDELT 三源、KB 自动回流、信号溯源 UI、种子库虚构占比降至 16.5%）
> - ✅ **M2 分析深度与 SQL 证据** `v2.3-analytics` — **本次完成**：`src/app/analytics/queries.py` 手写 SQL 指标层（8 图，≥5 条用窗口函数/CTE）、`/api/analytics/center` 端点、仿真器 `calibrated_from` 校准、前端分析中心（SVG 图表 + 可展开真实 SQL + 仿真角标）
> - ⏳ **M3 可执行闭环与 A/B** `v2.4-closed-loop` — **待做**
> - ✅ **M4 PM 文档与运行证据** `v2.5-pm-docs` — 已完成（指标体系 / 内容形态 / 规模化 / 真实运行报告 v1.1）
> - 🔧 **计划外已交付**：revise 机制（`v2-revise-mechanism`/`v2-revise-state`）、中文回译镜像（`v2-zh-mirror`）、M5 主题漂移四层防护（`v2.6`）、真实运行证据落盘（`v2.5.1-run-evidence`）。这些在原计划之外，但进一步补强了「真实感 + 人审闭环」叙事。

### M1 — 真实信号接入　`v2.2-real-signals`
**解决**：引擎入口是假的（最高优先级）

**改动**
- 新增 `src/app/sources/`：`gdelt.py` / `hackernews.py` / `reddit.py` / `base.py`
- `SignalScoutAgent` 输入源从「本地 KB 检索」改为「真实源拉取 → LLM 归纳信号」，本地 KB 降级为兜底
- 抓取结果**自动入 KB**（真实 URL、真实媒体、真实日期），替换 `example.com` 虚构语料
- `Signal` 模型新增字段：`source_url` / `source_name` / `published_at` / `engagement`(JSON: score/comments/tone) / `raw_lang`

**免费数据源（全部无需 API Key，已实测可达）**

> **实测调整（重要）**：原计划的 GDELT + HN(Firebase) + Reddit 三源，在沙箱/服务器 datacenter IP 下经实测：
> GDELT 持续 429 限流、Reddit 持续 403 封禁（datacenter IP 被拒）。因此主源调整为对服务器环境友好的
> **HN Algolia + Dev.to**（两者均免费、无 Key、返回真实互动数据、datacenter 友好）；GDELT 降级为
> **best-effort**（通了补本地化新闻，不通静默跳过）。这样即便生产环境也真实可跑，不赌会挂的源。

| 源 | 端点 | 提供的真实数据 | 角色 |
|---|---|---|---|
| HN Algolia | `hn.algolia.com/api/v1/search`（按市场关键词 + `date_range=past_month`） | **真实 points / num_comments**（人类投票与讨论） | 主源·按市场区分 |
| Dev.to | `dev.to/api/articles?tag=...&state=rising` | **真实 reactions / comments**，按 tag 覆盖类目 | 主源·稳定兜底 |
| GDELT DOC 2.0 | `api.gdeltproject.org/api/v2/doc/doc`（best-effort） | 全球新闻、按国家码过滤、tone | 增强·本地化新闻 |

HN / Dev.to 是英文技术社区，覆盖的是各市场 interests 主类目（ai/tech/business）——符合 SignalScout「跨市场信号也算相关」的设计。
GDELT 用 FIPS 国家码，市场映射：`US→US`、`JP→JA`、`KR→KS`、`BR→BR`、`CN→CH`。

**关键设计点（面试话术）**
> 「HN 的 score 和 Reddit 的 upvote 是**真实的人类内容消费信号**。我用它做两件事：一是让 TrendAnalyst 的热度判断有真实依据而非 LLM 臆测；二是用真实互动分布去校准后置仿真器的参数——所以我的仿真不是拍脑袋的随机数，是有真实锚点的行为模型。」

**验收**
- [ ] 五个市场各能拉到 ≥10 条真实信号，带可点击原文链接
- [ ] 断网 / API 挂掉时自动降级到本地 KB，主链路不裸奔（保持现有降级哲学）
- [ ] KB 中虚构 `example.com` 条目占比降到 30% 以下
- [ ] 控制台信号卡片显示真实来源、发布时间、真实互动数

### M2 — 分析深度与 SQL 证据　`v2.3-analytics`
**解决**：SQL 能力无证据、指标单薄、仿真不可信

**改动**
- **仿真器升级**：`simulator.py` 参数由 M1 抓到的真实互动分布拟合，函数签名带 `calibrated_from` 元信息；所有仿真数据在 UI 打「仿真」角标
- **新增指标（全部基于已有数据，无需新埋点）**
  - 供给效率：信号→发布 lead time、一次通过率、重写率、Agent 降级率
  - 成本：单条内容 token / 费用、单位质量分成本
  - 消费：内容衰减曲线（发布后 24/48/72h）、分市场 × 形态下钻
- **分析中心页面**（`ui/console` 新增 tab）
  - 漏斗图：曝光 → 点击 → 完读 → 互动
  - 分形态 / 分市场对比柱状图
  - 同期群：按发布批次的表现衰减
  - **每张图下方可展开「驱动此图的 SQL」，显示真实执行的 SQL 原文** ← 这是给面试官看的
- 新增 `src/app/analytics/queries.py`：所有分析用**手写 SQL**（不用 ORM），集中管理、可展示

**验收**
- [ ] 分析中心 ≥4 张图，全部可展开真实 SQL
- [ ] 至少 2 条 SQL 用到窗口函数或多级 CTE（下钻 / 同期群）
- [ ] 成本看板给出「单条内容 ¥X vs 人工 Y 分钟」的对照

---

### M3 — 可执行闭环与 A/B　`v2.4-closed-loop`
**解决**：闭环只到「建议」为止，无执行层

**改动**
- 新增 `PromptVersion` 表：`template_name` / `version` / `content` / `source`(human/ai_suggested) / `adopted` / `created_at` / `parent_version`
- `FeedbackAnalyst` 建议**结构化**：从自由文本改为 `{target_template, section, proposed_change, rationale, expected_metric}`
- 控制台「迭代建议」页：AI 提议 → 人审 → **一键采纳生成新版本** → 可回滚（完全复用 KBCurator 的 AI提议+人审闸门交互）
- **极简 A/B**：同一 angle 用 Prompt v1 / v2 各跑一次 → 两条内容 → 仿真 → 对比报告（质量分 / CTR / 成本）
  - 顺带交付「同一选题多版本改写」能力

**面试话术**
> 「我坚持 AI 不自动改系统，但『只给建议』确实缺执行层。所以做成**提议—人审—采纳—可回滚—下轮对比**。人依然是标准的定义者，但决策成本从『自己重写 Prompt』降到『点一下采纳』。这个模式我在 KB 治理上先验证过，直接复用到 Prompt 上。」

**验收**
- [ ] 采纳一条建议后，下次运行确实使用新版本 Prompt
- [ ] Prompt 版本可 diff、可回滚
- [ ] A/B 报告能展示两版差异与指标对比

### M4 — PM 文档与运行证据　`v2.5-pm-docs`（可与 M1 并行）
**解决**：文档全是技术视角，缺 PM 思维证据

**交付四份文档**
1. `docs/METRICS_FRAMEWORK_v1.0.md` — 供给引擎指标体系：北极星指标 + 四层分解（供给效率 / 内容质量 / 消费表现 / 成本效率）+ 每个指标的口径定义与数据来源
2. `docs/CONTENT_FORMAT_DESIGN_v1.0.md` — 内容形态设计：**为什么是这 4 种形态**、各自的消费场景 / 信息密度 / 钩子位置 / 适配平台，以及形态与市场档案的交叉矩阵
3. `docs/SCALE_DESIGN_v1.0.md` — 规模化设计：若日活千万、日产 10 万条，架构如何演进（队列 / 分片 / 缓存 / 成本模型 / 审核抽样率），**外加「已评估但未做」清单**（审核分层、DAG 编排、向量检索、多模态渲染，每项写清不做的理由）
4. `docs/RUN_REPORT_v1.0.md` — 真实运行报告：用 M1 的真实信号跑 30 条，交出成功率、失败归因分布、平均 lead time、平均成本、Rubric 五维分布、典型失败案例复盘

**验收**
- [ ] 四份文档均含数据或矩阵，不是纯论述
- [ ] README 增加「PM 设计文档」入口区块

## 2. 执行顺序与节奏

```
第 1 周   M1 真实信号接入        →  tag v2.2-real-signals
         （并行）M4 文档 1、2、3
第 2 周   M2 分析深度 + SQL      →  tag v2.3-analytics
         （M1 完成后）M4 文档 4 运行报告
第 3 周   M3 可执行闭环 + A/B     →  tag v2.4-closed-loop
         收尾：README 重写、Demo 数据快照更新  →  tag v2.5
```

**若时间只够做一件事：做 M1。** 入口真实化是唯一一个能把整个项目性质从「Demo」改成「系统」的改动。
**若只够做两件事：M1 + M4。** 一个补真实感，一个补 PM 视角，正好覆盖两个最大短板。

## 3. 提交规范

沿用现有约定：小粒度提交 + 语义化消息（`feat:` / `fix:` / `refactor:` / `docs:` / `data:`），里程碑打 annotated tag 并推 `master:main`。
**Git 历史本身就是交付物**——commit history 要能读出「接真实数据源 → 补分析深度 → 建可执行闭环」这条迭代路径。

## 4. 需要注意的坑

- 部署分支是 `master:main`，Render 免费实例磁盘易失，每次从 `demo_snapshot.db` 重建 → **M1/M2 改完必须同步更新种子快照**，否则线上回退旧数据
- 真实源拉取要做超时与缓存，Render 免费实例冷启动慢，别让首屏卡在外部 API 上
- 抓取遵守各站 robots 与频率限制，Reddit 必须带自定义 User-Agent
- deepseek-v4-flash 是推理模型，reasoning token 与正文共用 max_tokens → 新增的结构化输出（如建议 JSON）继续走切片策略
