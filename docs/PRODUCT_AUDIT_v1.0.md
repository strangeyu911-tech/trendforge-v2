# TrendForge V2 产品与用户体验审计 v1.0

> 审计对象：<https://trendforge-v2-web.onrender.com>（控制台 /console/）+ 后端 API + 本地快照库
> 审计视角：产品经理 / 第一次打开这个 Demo 的用户（= 面试官）
> 审计日期：2026-09-12
> 方法：通读 `ui/console/assets/app.js`(1905 行) 全部 9 个视图、后端 8 个 router、`analytics/queries.py`、`simulator.py`、`workflow/ab.py`，并抓取线上真实数据对照

---

## 0. 一句话结论

**架构与工程能力已经超过作品集及格线不少，但「Demo 数据」和「面向人话的呈现」正在反向拖垮它。**

现在的第一印象是：打开控制台 → 内容页 13 条有 12 条挂着「需修改」红标、8 条挂着「兜底」橙标 → 分析中心第一张图北极星指标 = 0% → 评估中心报告区为空、四个 KPI 全是仿真数据却没标注。

一个不了解背景的人会在 30 秒内得出「这个系统产出的内容全都不合格」的结论。**这是当前最大的风险，优先级高于任何新功能。**

## 1. 先回答你直接提的两个问题

### 1.1 「迭代闭环这个模块有点莫名其妙，好像没有存在的必要」

**结论：不能删，但它现在的产品形态是错的，必须重构。**

**为什么不能删**（删掉的代价）：

| 删掉后失去的东西 | 为什么重要 |
|---|---|
| 「AI 提议 → 人审 → 生效 → 可回滚」的可执行证据 | 这是你整个项目立论「人定义标准，AI 在标准内进化」的**唯一闭环证明**。KBCurator 只覆盖了知识库，Prompt 侧删了就断 |
| M3 的技术资产 `PromptManager` 运行时覆盖层 | 采纳即生效、无需重启，这是有工程含量的能力，没有承载页面就白写了 |
| FeedbackAnalyst 的落地价值 | 没有采纳流，它就退化成「又一个生成报告的 Agent」，和 Editor 的区别说不清 |

**但它现在确实「莫名其妙」，有 5 个真因：**

1. **它是开发者工具，被放进了运营控制台。**
   整页词汇是 `writer` / `editor` / `angle_editor`、`v1` / `v2`、`diff`、`adopted`。运营用户（和面试官）看到的是一堆工程标识符，读不出「这页在解决我的什么问题」。

2. **它证明不了自己有用 —— 这是最根本的一条。**
   采纳一条建议 → 生成 v3 → toast 提示「下一轮运行即生效」→ **然后就没有然后了**。
   系统从没告诉过用户「采纳之后，新产出的内容质量从 3.2 涨到了 3.8、通过率从 0% 到了 60%」。
   **闭环缺了「效果回收」这最后一段，所以点了感觉没反应。** 用户感觉到"莫名其妙"，本质上感觉到的是这个。

3. **和评估中心功能重复。**
   评估中心有「运行 FeedbackAnalyst」按钮（`app.js:1062`），闭环页 ① 也有一个（`app.js:1533`）。同一动作两个入口，且两个页面的产出还互相跳转。

4. **A/B 的判定逻辑站不住 —— 面试被追问会很难堪。**
   `simulator.py:97`：`ctr = 0.02 + 0.08 * q_mod * fmt_mod * random.uniform(0.8, 1.2)`
   - 两版 Prompt 的质量差异通常只有 0.1–0.4 分 → 折算 CTR 差异约 1–2 个百分点；
   - 而随机噪声是 **±20%**，比信号本身还大；
   - 更关键的是 **CTR 是由 quality 算出来的**（`q_mod = 0.5 + quality/5`），再用 CTR 去「验证」Prompt 对 quality 的改善，是**循环论证**。
   现在的 A/B 结论基本等于掷骰子，页面上却写得很像结论（`v2 − v1 / 质量 +0.2 · CTR +0.011`）。

5. **线上跑不动。**
   A/B 要求选两个 Prompt 版本，但 `seed.py` 只登记 v1；快照库里只有 `writer` 有 v3（M3 实跑留下的），其他 15 条 prompt 记录全是 v1 → 下拉里选不出第二个版本，③ 区在 Demo 上是「能看不能用」。

**重构方案（保留能力，换形态）：**

| # | 改法 | 成本 |
|---|---|---|
| 1 | 改名：迭代闭环 → **「系统进化」**，副标题一句话说人话：「这里决定 AI 下一轮怎么写。所有改动都由你确认，可随时回滚。」 | 5 min |
| 2 | **补上第四段「效果回收」**：采纳后，用 `tasks.prompt_versions`（已落库！）把「采纳前 N 条」与「采纳后 N 条」的质量均分 / 裁决分布 / 单条成本做对比卡片。**这一段补上，闭环才真的闭合，而且有 SQL 证据可讲。** | 半天 |
| 3 | A/B 去掉「CTR 谁赢」的结论式表达：只保留质量分 diff + 成本 diff + **让人二选一**（你选哪一版），CTR 降为灰色参考值并注明「仿真口径，不作为决策依据」 | 1 h |
| 4 | 删掉评估中心的 FeedbackAnalyst 按钮（或改成「生成迭代建议 →」跳走到系统进化审批），一个动作只留一个入口 | 20 min |
| 5 | 模板名/版本号加中文映射：`writer→写作`、`editor→总编审核`、`angle_editor→角度设计`；`v3` 显示为「第 3 版（AI 提议 · 已生效）」 | 1 h |

### 1.2 「评估中心和分析中心还有 brief_news / card / video_script 这种字符」

**对，而且比你看到的更多 —— 共 11 处，清单如下。**

根因：前端只在**少数几处**（内容列表形态列、分发计划、市场档案平台）做了枚举翻译，而**分析中心的图表渲染函数直接把后端返回的原始字段值画在图上了**（`svgBar` / `svgHeat` / `svgGroupedBar` 的 `String(r[0])`）。后端 `queries.py` 返回的正是数据库里的英文枚举。

| # | 位置 | 暴露的内容 | 代码定位 |
|---|---|---|---|
| 1 | 分析中心 · 分形态×市场 CTR 热力图（行标签） | `article` `video_script` `card` `brief_news` `comment` | `queries.py:348` → `app.js:1504` `svgHeat` |
| 2 | 分析中心 · 分形态人均阅读时长（柱标签） | 同上 | `queries.py:394` → `app.js:1404` `svgBar` |
| 3 | 分析中心 · Agent 降级率（柱标签） | `signal_scout` `trend_analyst` `format_adapter`… | `queries.py:195` → `svgBar` |
| 4 | 分析中心 · Rubric 五维（图例） | `accuracy` `angle` `readability` `local_fit` `engagement` | `queries.py:281-284` → `app.js:1493` |
| 5 | 分析中心 · 消费漏斗（阶段名中英混排） | `曝光 Exposed` `点击 Clicked` `完读 Finished` `互动 Liked+Shared` | `queries.py:117-122` |
| 6 | 跑供给 · 运行历史「类型」列 | `ab` `feedback` `revise` `kb_curate` | `app.js:504` `${esc(x.kind)}` |
| 7 | 内容详情 · Trace 页 | `signal_scout` / `format_adapter` / `deepseek-v4-flash` | `app.js:987` `${esc(s.agent)}` |
| 8 | 内容详情 · 质量 Tab | `topic_guard` `evidence_guard` `_revise` `fact_check` 内部键 | `app.js:953` `kvTree` 未覆盖的 key |
| 9 | 评估中心 · 评估报告建议 | `[writer/结构要求（首段必须兑现钩子）] …` | `feedback_analyst.py:74` 字符串拼接 |
| 10 | 迭代闭环整页 | `writer` `editor` `v1` `v2` `diff` 原文 | `app.js:1599/1638` |
| 11 | 知识库 · 类目分布 | `ai` `tech` `business` `entertainment` `sports` `ev` | `app.js:1122` `${k}` |

**修法（推荐在前端加一层统一翻译，不要改后端返回结构）：**

```js
// 所有图表/标签渲染前统一过一遍，未知 key 原样返回（保证不丢信息）
const LABEL = {
  ...FMT_META 映射, ...AGENT_LABEL, ...DIM_LABEL, ...KIND_LABEL, ...CATEGORY_LABEL,
};
const lb = (s) => LABEL[String(s)] ?? String(s);
```
然后在 `svgBar` / `svgHeat` / `svgGroupedBar` / `svgFunnel` / 表格渲染里把 `String(r[0])`、`ser.name`、`x.kind`、`k` 全部替换成 `lb(...)`。
**预计 1.5 小时改完，视觉专业度提升最明显的一笔投入。**

### 2.5 内容详情（这是产品最核心的一页）

## 3. 全局级问题（跨模块）

### 3.1 P0 · Demo 数据把产品讲成了失败案例

线上 13 条内容的真实分布（已从 API + 快照库双向核实）：

| 指标 | 线上实际值 | 给人的印象 |
|---|---|---|
| 裁决为 pass（可发布） | **0 / 13** | 系统从未产出合格内容 |
| 裁决为 revise（需修改） | 12 / 13 | 满屏红色 |
| is_fallback（含兜底环节） | 8 / 13 | 超过一半没走真实 LLM |
| 质量均分区间 | 1.2 – 4.4，均值 3.3 | — |
| 北极星 QSR | **0.0%**（合格 0 / 尝试 15） | 分析中心首图 |
| 供给成功率 | 60%（done 9 / failed 5 / rejected 1） | 仪表盘第二个 KPI |

需要说明的是：**本地 `trendforge_v2.db` 里其实有 3 条 pass 内容（GB/IN）、7 个市场、13 条真人校准分**——这些更能代表系统的真实水平，但**没有同步进 `demo_snapshot.db`**，所以线上看到的是一份更差的旧数据。

### 3.2 P0 · 线上快照与本地库分叉

| 项 | demo_snapshot.db（线上） | trendforge_v2.db（本地） |
|---|---|---|
| 市场数 | 5 | **7**（多 GB/IN） |
| 内容数 | 13（0 条 pass） | 16（**3 条 pass**） |
| human_calibrations | **表不存在** | 13 行 |
| eval_reports | 0 | 0 |
| prompt_suggestions | 1 | 1 |

### 3.3 P0 · 真实/仿真标注口径不一致

分析中心有角标 → 评估中心没有（同样的数据源）；内容页有「合成 KB」提示 → 知识库页没有。
**建议统一为一条铁律：凡是仿真/合成的，所在区块必须自带角标，不依赖用户去别的页面看说明。**

### 3.4 P1 · 命名不统一

Agent 中文名两套（首页 vs 控制台，10/11 不一致）；形态在部分页面中文、部分页面英文；模板名/维度名/任务类型名直接暴露英文。
**建议建一张全局枚举表（前端一个 LABEL 常量 + 后端 spec 里带 labels），一次改完。**

### 3.5 P2 · 死功能与未接线数据

- `bad_cases` 表有 3 条数据，**前端零入口**（PRD 里的 BadCase 库没做 UI）。
- `GET /api/prompts`（`misc.py:52`）前端未使用（用的是 `/prompts/versions`）。
- `GET /api/bad-cases` 同样无消费者。

### P0 · 半天，直接决定第一印象
